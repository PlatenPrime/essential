# Context — React Context

> Актуальность: сентябрь 2026

## Роль в системе

Встроенный канал передачи данных вниз по дереву без prop drilling. Архитектурно Context — для **относительно стабильных** зависимостей UI (тема, локаль, auth-снимок, DI-конфиг), не для высокочастотного серверного кэша.

## Что нужно знать (80/20)

- Provider задаёт значение для поддерева; consumer подписан на изменения этого значения
- Любое новое значение Provider → ре-рендер всех consumers (если нет мемоизации/разбиения)
- Разделяй «часто меняется» и «редко меняется»: отдельные context или selector-паттерны / внешние сторы
- Context ≠ глобальный store из коробки: нет middleware, нормализации, devtools — это примитив DI/проброса
- Типичные уместные кейсы: theme, i18n, текущий user/session snapshot, feature flags UI
- Неуместные: список сущностей с частыми апдейтами, форма на каждое нажатие клавиши, server cache
- Граница с Client Components: Provider с state обычно на client; server может передать начальный снимок props/context по правилам стека

## Развилки

| Развилка | О чём спор (одна строка) |
| --- | --- |
| Context vs внешний store (Zustand и т.п.) | Простота React API vs контроль подписок и частоты апдейтов |
| Один широкий Provider vs много узких | Меньше wiring vs меньше лишних ре-рендеров |
| Prop drilling vs Context | Явный контракт vs удобство глубокого дерева |
