# Composition — композиция компонентов

> Актуальность: сентябрь 2026

## Роль в системе

Способ собирать UI из меньших частей: кто владеет разметкой слотов, кто — данными, кто — поведением. Архитектурно композиция важнее наследования: границы ответственности видны в дереве props/children, а не в иерархии классов.

## Что нужно знать (80/20)

- `children` / slots — основной канал расширения без форка компонента
- Containment vs specialization: обёртка с дыркой vs готовый «экран целиком»
- Поднятие state: общее состояние живёт у ближайшего общего предка, не «везде»
- Presentational vs container — эвристика разделения UI и wiring, не обязательная папка-структура
- Compound components (Tabs.List / Tabs.Panel) — неявный контракт через Context; сила UX API vs скрытая связь
- Render props / headless + UI: логика отдельно, внешний вид снаружи — цена indirection
- Избегать god-component: если файл знает и данные, и роутинг, и все экраны — дробить по границам фичи

| --- | --- |
| Много мелких компонентов vs несколько крупных | Переиспользование vs читаемость фичи в одном месте |

| Headless UI vs готовые kit-компоненты | Контроль a11y/стилей vs скорость поставки |
